

## 一、问题背景

当前月结请款单按照入库单生成。单个供应商一个月可能存在 500～1000 条入库明细，同时月结过程中还需要使用预付余额进行抵扣。

当前问题主要表现为：

- 请款单明细数量过多，页面加载、编辑和提交严重卡顿；
- 预付金额需要从预付余额中取用，并与大量入库明细关联；
- 系统可能逐条计算、逐条校验、逐条核销，导致处理时间过长；
- 技术基于现有实现方式判断“无法实现”。

## 二、结论

500～1000 条数据本身并不是 ERP 无法处理的数据量。

真正的问题是当前产品模型可能把以下职责全部压在同一张请款单中：

1. 入库明细查询；
2. 供应商月度对账；
3. 应付金额确认；
4. 预付款抵扣和分摊；
5. 实际资金请款；
6. 审批、核销和审计追溯。

因此，技术所说的“无法实现”，更准确的表述应当是：

> 按照现有逐条加载、逐条计算、逐条核销的处理方式，系统难以支撑大批量月结，需要调整产品模型和技术处理方式。

## 三、核心产品原则

### 1. 来源于入库单，不等于请款单必须直接承载全部入库单

入库单是应付金额的来源依据，但请款单不应成为承载所有业务明细的巨型表单。

月结审批真正关注的是：

- 本期应付总额；
- 本期扣款或调整金额；
- 使用预付款金额；
- 本次实际付款金额。

具体对应的 500～1000 条入库明细，应保存在底层关联关系中，支持查询和追溯，而不是全部直接铺在请款单操作界面。

### 2. 底层保留明细，操作层使用汇总

产品设计应同时满足：

- 入库级追溯；
- 供应商对账；
- 财务审核；
- 预付款核销；
- 页面和提交性能。

正确方向不是删除明细，而是增加汇总层。

## 四、推荐业务架构

```text
入库单
  ↓
采购应付明细
  ↓
供应商月结对账单
  ↓
预付款抵扣
  ↓
请款单
  ↓
付款与核销
```

## 五、模块设计

### 5.1 采购应付明细

每张入库单生成一条或多条采购应付明细。

建议字段：

- 公司主体；
- 供应商；
- 采购单号；
- 入库单号；
- 入库日期；
- 结算月份；
- 币种；
- 入库金额；
- 调整金额；
- 已结算金额；
- 未结算金额；
- 应付状态；
- 月结单号；
- 请款单号。

该模块负责保留最底层的应付来源和追溯关系。

### 5.2 供应商月结对账单

月结时，不直接使用 500～1000 张入库单生成请款单，而是先按照以下维度生成月结对账单：

```text
公司主体 + 供应商 + 币种 + 结算月份
```

月结对账单汇总示例：

| 项目 | 金额 |
|---|---:|
| 本期入库应付 | 1,000,000 |
| 退货扣款 | -20,000 |
| 质量扣款 | -10,000 |
| 价格调整 | -20,000 |
| 本期应付总额 | 950,000 |
| 使用预付款 | -200,000 |
| 本次实际请款 | 750,000 |

页面默认展示汇总金额。

底层入库明细采用：

- 分页加载；
- 按需展开；
- 服务端筛选；
- 按采购单、入库单、日期查询；
- 支持导出；
- 默认不一次性加载全部明细。

### 5.3 预付款抵扣

用户在月结单上只录入或确认本次使用的预付款总额，例如 200,000 元。

系统再按照规则在后台将金额分摊到具体应付明细。

建议支持以下核销规则：

#### 规则一：按应付时间先后核销

优先抵扣最早产生的未结算应付明细。

适合作为默认规则。

#### 规则二：按采购单绑定核销

如果预付款本身关联采购单，则优先抵扣该采购单产生的应付。

#### 规则三：人工指定范围

特殊情况下，用户可指定：

- 某一采购单；
- 某一批采购单；
- 某一结算期间；
- 部分应付明细。

人工操作应尽量停留在采购单或汇总层，不建议要求用户在 1000 条入库明细中逐条勾选。

### 5.4 预付款余额占用机制

预付款账户需要区分：

```text
预付款总额
- 已核销金额
- 已占用金额
= 可用余额
```

示例：

| 状态 | 金额 |
|---|---:|
| 预付款总额 | 300,000 |
| 已核销 | 50,000 |
| 审批中已占用 | 200,000 |
| 可用余额 | 50,000 |

状态流转：

```text
可用 → 已占用 → 已核销
             ↘ 审批驳回或撤回后释放
```

这样可以避免多张月结单或请款单重复使用同一笔预付款。

### 5.5 请款单轻量化

请款单只负责资金申请，不直接复制和实时处理全部入库明细。

请款单头建议包含：

- 公司主体；
- 供应商；
- 币种；
- 结算月份；
- 月结对账单号；
- 本期应付金额；
- 扣款及调整金额；
- 预付款抵扣金额；
- 本次实付金额；
- 收款账户；
- 付款方式；
- 预计付款日期。

资金结构示例：

| 资金类型 | 金额 |
|---|---:|
| 本期确认应付 | 950,000 |
| 预付款核销 | -200,000 |
| 银行实际付款 | 750,000 |

底层关联关系：

```text
请款单
  → 月结对账单
  → 采购应付明细
  → 入库单
```

用户可下钻追溯，但请款单本身不承载全部业务操作。

## 六、技术实现建议

### 6.1 前端

- 默认加载月结汇总，不默认加载全部明细；
- 明细采用服务端分页，每页 50～100 条；
- 大表格使用虚拟滚动；
- 查询和筛选在服务端执行；
- 不将 1000 条明细全部放入前端表单状态；
- 展开明细时按需请求；
- 预付款录入总额后，不在前端逐条实时重算；
- 批量选择只保存条件或选中范围，不反复提交完整明细对象。

### 6.2 后端

- 使用批量查询和批量写入；
- 禁止在循环中逐条访问数据库；
- 避免 N+1 查询；
- 汇总金额使用预计算或汇总快照；
- 月结生成和核销分摊可采用异步任务；
- 提交时先校验并占用预付余额；
- 后台批量生成核销分摊记录；
- 使用幂等号，防止重复点击导致重复生成；
- 针对供应商、月份、采购单、入库单、状态建立合理索引；
- 避免每处理一条明细都重新扫描完整预付流水和应付明细。

### 6.3 建议数据对象

- 采购应付明细；
- 供应商月结单；
- 供应商月结单明细；
- 预付款账户；
- 预付款流水；
- 预付款占用记录；
- 预付款核销记录；
- 预付款核销分摊明细；
- 请款单；
- 付款单。

## 七、落地方案

### 方案一：最小改造

适合短期解决性能问题。

主要改造：

- 保留现有请款单来源逻辑；
- 页面改为汇总展示和分页加载；
- 预付抵扣只填写总金额；
- 后台自动分摊至具体入库明细；
- 提交采用批量处理或异步任务。

优点：

- 改动范围较小；
- 可快速缓解卡顿；
- 不改变主要业务流程。

缺点：

- 请款单仍承担较多职责；
- 后续遇到扣款、退货、调价、反核销时仍可能复杂。

### 方案二：增加供应商月结对账单

推荐方案。

流程：

```text
入库单 → 采购应付明细 → 月结对账单 → 请款单
```

月结对账单负责：

- 汇总入库应付；
- 供应商对账；
- 扣款和调整；
- 预付款抵扣；
- 生成最终应付金额。

请款单负责：

- 实际资金申请；
- 审批；
- 付款。

优点：

- 业务对账和资金请款职责清楚；
- 请款单性能稳定；
- 保留完整追溯关系；
- 便于后续建设账龄、供应商余额和月结关账。

### 方案三：建设应付与预付核销中心

长期完整方案。

建设内容：

- 应付明细台账；
- 预付款台账；
- 预付占用和释放；
- 自动核销规则；
- 人工核销；
- 反核销；
- 红冲；
- 供应商余额；
- 应付账龄；
- 月结关账控制。

优点：

- 财务模型完整；
- 可支撑更多复杂业务；
- 可减少后续重复改造。

缺点：

- 实施范围大；
- 对现有采购、入库、财务和付款流程影响较广。

## 八、不建议采用的处理方式

### 8.1 强制拆成大量请款单

虽然可以暂时降低单据明细数量，但会造成：

- 审批单数量暴增；
- 财务无法一次看到完整月结金额；
- 预付款可能重复占用；
- 对账工作量增加；
- 供应商一张账单对应多张系统单据。

只能作为临时兜底，不适合作为长期产品方案。

### 8.2 单纯增加接口超时时间

只能暂时延后报错，不能解决：

- 页面卡顿；
- 数据库重复查询；
- 逐条处理；
- 锁表；
- 重复计算。

### 8.3 删除入库明细，只保留汇总金额

会失去：

- 审计依据；
- 入库追溯；
- 供应商对账依据；
- 差异排查能力。

正确方式是底层保留明细、上层汇总操作。

### 8.4 要求用户逐条分配预付款

这是把系统计算工作转嫁给用户。

在 500～1000 条明细的情况下，操作成本和出错风险都不可接受。

## 九、与技术评审时的表达

可以向技术明确提出：

> 本次需求不是要求前端页面一次性渲染并同步处理 1000 条入库明细。入库单仍然作为应付来源，但月结过程需要增加汇总层。请款单只处理月结应付总额、预付款抵扣总额和实际付款金额，具体入库明细及预付款分摊由后台批量或异步生成。请技术基于服务端分页、汇总快照、批量核销、余额占用和异步处理重新评估，而不是基于现有逐条实时处理模式判断无法实现。

## 十、推荐结论

优先建议采用：

```text
供应商月结对账单
+ 轻量请款单
+ 预付款占用机制
+ 后台自动分摊
+ 明细分页和按需加载
```

该方案可以同时解决：

- 大批量明细卡顿；
- 预付款重复使用；
- 月结对账困难；
- 请款单过重；
- 入库单追溯；
- 财务审核；
- 后续应付账龄和供应商余额建设。

## 十一、待业务确认问题

1. 月结维度是否固定为公司主体、供应商、币种和月份？
2. 同一供应商是否存在多个采购组织或结算主体？
3. 预付款是否必须绑定采购单？
4. 未绑定采购单的预付款默认如何分摊？
5. 是否允许用户修改系统自动分摊结果？
6. 扣款、退货、质量赔偿、价格调整分别由谁录入？
7. 月结单确认后，是否允许新增或移除入库明细？
8. 月结单审批中是否锁定入库应付明细？
9. 审批撤回或驳回时，预付占用是否自动释放？
10. 付款后是否允许反核销，反核销权限归谁？
11. 是否需要生成供应商确认版对账单？
12. 是否存在跨币种预付款抵扣？
